# ADR-0020: Fault injection (G10a)
- Status: accepted (G10a); written before the first run, so nothing here is a result. Measured values and manifest filenames are added after the runs of record, in ADR-0015's style. Items marked **unverified** are reasoning from code and specs that no run has confirmed yet.
## Decision
The six faults of the G10a subset (PLAN G10a, design §5: F1, F2, F3, F4, F5, and F6 as F6a + F6b) are scripted against the real interfaces: Docker, the Kafka protocol, the Connect REST API, the Spark checkpoint directory and Postgres DDL. All randomness comes from one seeded `random.Random`. The design §5 rows are not edited; deviations are dated notes there (2026-11-05) and are listed below.
- **Order on one shared stack: F4, F1, F2, F3, F5, F6a, F6b, then an END step.** F4 needs a connector that has never been created, so it must run first and cannot be re-run on a used stack. F1 and F2 need quiet periods and fresh records. F3 and F5 run under load. F6 goes last because its schema changes and out-of-band writes end the ground-truth oracle's validity.
- **Each fault is wrapped.** A `run_fault` wrapper runs the injection in try/except, restores the stack in a `finally` (fault file cleared, Connect, Redpanda and `spark-streams` up, load stopped, subject compatibility reset, connector config restored), then runs the reconciliation gate (ADR-0021). A `preflight` check runs before every injection: services running, connector and task RUNNING, no fault file, no generator container, live connector config equal to the rendered `pg-shop.json`. If preflight fails, the remaining faults are recorded as skipped and the manifest is written; the harness does not inject into a broken stack. If a gate fails but preflight passes, the run continues for diagnosis only, later gates report only new mismatches against those carried, the fault record names the earlier fault as the possible contaminant, and the run still fails overall.
- **Hooks are inert by default.** The kill points in `streams.py` act only when `ADRP_FAULT_HOOKS=1` and the fault file names them. Measurement runs (G11a) leave the variable off, so they contain no faults. The existing parked hook keeps its behaviour and never writes ids.
## The faults
| Fault | Injection | Recovery | Notes |
|---|---|---|---|
| F4 connector crash mid-snapshot | Create the connector with test-only snapshot overrides (small fetch size, a throttled snapshot query on `transactions`) so a kill lands inside the snapshot; `docker kill` the Connect container when the topic holds some but not all rows. | Writers stop, Connect restarts, the unmodified `pg-shop.json` is re-applied and the live config is asserted equal to it. | The override property names are to be confirmed on Debezium 3.7 at the first run (**unverified**). The overrides exist only to make the kill land; the config is restored afterwards. |
| F1 duplicate events | Silver: stop `spark-streams`, remove the last few entries of `silver/offsets` and `silver/commits` (and their `.crc` siblings), restart. Bronze: a batch Kafka read of a recorded offset range, appended to bronze by `fault.py replay-bronze`. | None. Silver is expected to self-heal; bronze keeps the duplicates by design. | The bronze duplicate ledger uses the count actually read, never the requested range. That a stale `.crc` would break a rewritten checkpoint file is **unverified**. |
| F2 out-of-order updates | Read raw bytes of recent records, re-produce older versions of seeded keys with identical key and value bytes to the same partition, after the newer ones. For one scripted ad-hoc `help_articles` row (insert, update, logical delete), re-produce its insert and update after the logical delete. | None. | The ad-hoc case is the resurrection test: an older insert after a logical delete must not bring the row back. Records are produced right after a fresh burst, while they are younger than the compaction lag. |
| F3 Spark kill mid-MERGE | One kill at the existing parked `mid_merge` point, plus up to three in-flight kills at a new non-parking `merge_start` hook placed immediately before `silver.merge_changes`, fired by the host after a seeded delay, under load. | Fault file cleared, `spark-streams` restarted, load stopped after a settling period. | See the two limits below. |
| F5 Redpanda restart | `compose restart redpanda` under load, 30 s in, load continues after the broker is healthy. | Wait for the broker, restart the connector task if it failed, record whether Spark restarted itself, otherwise bring it up. | A graceful restart only, on a broker running `--mode=dev-container`. No claim about acknowledged-write durability, and no claim about a hard broker crash. |
| F6a add column | `g3.phase_add_column` under load. | None. | Reuses g3's three checks, renamed with an `F6a:` prefix. |
| F6b incompatible change | `g3.phase_quarantine` (rename plus type narrowing) with the generator stopped. | One no-op update of the refund that was parked, so Postgres emits a CDC update with the restored schema. | See the registry note below. |
The END step stops the writers, counts and removes Iceberg orphan files with `forget.remove_orphans_now` and `older_than = now` (ADR-0018 reasoning: writers are stopped, so no in-flight write can be taken for an orphan; ADR-0015's 24 h applies when writers run), restarts, runs a final gate and scores the fault table.
## Why silver is rewound but bronze is replayed by append
Silver is rewound by editing its checkpoint, which is what "reset the consumer to replay an offset range" means for a query whose MERGE is guarded by the LSN condition. Bronze is **not** rewound. The native Iceberg sink records the query id and epoch in the snapshot summary and skips epochs it has already committed. If bronze's checkpoint were rewound, replayed batch ids at or below the last committed epoch would be skipped, and new data arriving in those ids could be lost. This is **unverified**: it is inferred from the sink's documented behaviour and was not spiked. Because of it, bronze duplicates come from a batch append of a recorded range, which is deterministic and countable. This is a dated note on design §5 F1 ("replay silver's checkpoint, append to bronze"); the F1 row is unchanged.
## Limits
- **The parked `mid_merge` hook does not sit inside an Iceberg write.** It parks between two tables' MERGEs in one batch (`streams.make_batch_handler`), so a kill there leaves earlier tables committed and later ones not; it does not interrupt a write. The G8 run of record's orphan count matched the one orphan it had planted after a `mid_merge` SIGKILL, which suggests (**unverified**; how that count aggregates across tables was not checked) that this kill left no real orphan. The `merge_start` kills are in flight but are not guaranteed to land inside a data-file write either. Therefore the design §5 F3 expectation "orphan files left for G8 cleanup" is not asserted: the END step counts orphans and reports the count, and a count of zero is reported as "none observed", not failed.
- **The retried snapshot is tested without concurrent writers.** After F4's crash the replication slot already exists, so the retry cannot use the exported snapshot; it takes a fresh transaction at some later LSN. A transaction whose change LSN is below that snapshot LSN but which commits after it could yield an `r` row carrying the old value, after which its later `u` event would lose against the `s.lsn > t.lsn` guard. This would be silent staleness. It is **unverified**, no existing check exercises it (g3, g6 and g8 snapshot an empty database; g2 has no Spark), and G10a does not test it: writers are stopped before the restart. F4 is therefore described as "idempotent under the tested faults, with no writers during the retry", never as safe in general. Whether to add a deterministic reproduction (a transaction held open across the retry) is an open decision for the user; it would probably fail and need a merge change such as ordering `r` rows below streaming events, which is scope growth.
- **Registry gate bypassed in F6b.** `g3.phase_quarantine` sets the subject's compatibility to `NONE` so the incompatible schema can be produced, and ADR-0014 notes that BACKWARD accepts a rename. F6b is scored as caught by silver's quarantine, never by the registry. `contracts-ci` covers the registry separately.
- **F6b has no oracle.** The phase changes generator-owned `view_count` out of band, so Postgres remains the reference and the ground-truth log is not used after it.
- **F2 and compaction.** A re-produced old record takes the highest offset for its key, so on a compacting topic it can outlive the newer record. Silver stays correct, but the topic is then not a safe source for a rebuild; see ADR-0022.
- **F13 is not a seventh fault.** G10a adds no injection for the TOAST placeholder. Every gate counts `__debezium_unavailable_value` in silver (ADR-0021) and the fault table reports that count in the F13 row.
- One machine, one seed, and the number of runs is stated in each manifest. Nothing here extrapolates to production scale.

## Dated notes
- **2026-11-05, first live run (90/133), F5: Connect stalled silently after the broker restart (finding, not fixed).** After `compose restart redpanda` (broker down about 2 s) Connect kept reporting the connector and its task RUNNING for the remaining 55 minutes of the run, while `confirmed_flush_lsn` stayed frozen, the topics' high watermarks stayed frozen, and the Postgres walsender stayed `active` and kept receiving WAL. A thread dump showed the source task thread blocked in `BaseSourceTask.performCommit` -> `OffsetStorageReaderImpl.offsets`, waiting on a read of `_connect_offsets`, whose `KafkaBasedLog` work thread was spinning in `readToLogEnd` (about 6200 fetches per second against Redpanda, Connect at 56% CPU, about 1600 s of CPU in that thread). Spark was caught up to every high watermark throughout, so the F5, F6a, F6b and END mismatches (missing and differing rows, and the "resurrected" rows, which were logical deletes still in the unforwarded part of the WAL) are the unforwarded changes and nothing else. No data was lost: after `compose restart connect` the connector resumed from its committed offsets and a reconcile of the same dirty stack was clean (10 of 10 gate checks, Qdrant included, bronze missing 0, beyond end 0). The stall was not self-healed (an operator restart of Connect was needed) and the connector-status detection could not fire, because the status never left RUNNING. It did not recur in three later F5 runs on a freshly restarted Connect (1 stall in 4 F5 runs), so it is intermittent, and its cause is **unverified**: the suspect is the Kafka client's `metadata.recovery.strategy=rebootstrap` interacting with the restart (the clients logged rebootstrapping during the outage), but no run has shown that changing it prevents the stall.
- **2026-11-05, F5 check added.** "Connector and task RUNNING" does not show that changes are forwarded, so F5 now also requires `confirmed_flush_lsn` to advance under load after recovery (up to 60 s plus 150 s). The sampler window still ends at recovery, so the "sampled through the outage" check covers the broker outage only (3 samples for a 6 s window at a 2 s poll), not the period after it. No threshold was changed; a stall like the one above is visible in the exporter only as slot lag growing without a fall, far below the 1 GiB alert level.
- **2026-11-05, sampler poll interval 2 s to 0.5 s.** A compacting run failed only the F5 check "slot lag and connector status were sampled through the outage" with 2 answered samples: the window runs from injection to the first RUNNING connector read (about 4 to 6 s) and a 2 s poll can give fewer than the required 3 when recovery is fast. The condition (`>= 3` answered samples) is unchanged; the poll is now 0.5 s, with a 1 s scrape timeout. One exporter scrape took 15 to 70 ms when measured on the idle stack, so a 0.5 s poll yields about 8 samples in 4 s. Scrapes are serial in one thread and the sleep is the interval minus the scrape time, so a blocked scrape delays the next one but nothing queues. The F4 check only requires one answered sample in its window and does not depend on the cadence. The earlier note above states the 2 s figures of the first runs.
