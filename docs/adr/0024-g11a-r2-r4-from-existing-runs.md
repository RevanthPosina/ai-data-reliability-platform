# ADR-0024: G11a reduced to R2 and R4 from existing runs; R1 deferred
- Status: accepted (G11a, reduced scope, 2026-11-10). The Decision section holds no measured numbers; the numbers are in the Measured section, which cites committed manifests. Items marked **unverified** are not observed.
## Decision
**Scope (decided by the user on 2026-11-10 to avoid multi-hour live runs).** G11a is done in two parts. R2 (deletion lag) and R4 (idempotency) are filled from run manifests that are already committed. R1 (freshness per sink against achieved change rate) is **deferred**: nothing is measured for it now, and the README says so. No Docker command and no `make g*-check` is run for this decision. Everything below is an analysis of existing manifests by `notebooks/g11a_results.py` (DuckDB `read_json` over the manifests; logic in `adrp.measure.report`), and `make g11a-results` regenerates it and checks the README cells.
**No new runs, and why.** R2 is a property of the forget code and the g8 check, and R4 of the pipeline code that the G10a and G3 runs exercised. The reasoning for reusing the manifests is that those code paths are unchanged since the runs of record: between the two g8 code SHAs (`cc603c2` and `e0fe4be`) the forget code and `scripts/g8_check.py` are identical (the notebook shows `git diff --stat cc603c2 e0fe4be -- src/adrp/forget scripts/g8_check.py`; empty output means identical). The G10a work that landed between those SHAs added the reconciler, a fault harness, new `probe.py` subcommands and the Spark fault hooks in `streams.py`; the new hooks act only when `ADRP_FAULT_HOOKS=1` and the fault file names them, and the existing parked `mid_merge` hook that the g8 check uses keeps its behaviour (ADR-0020). That the g8 check behaves the same with the changed `streams.py` is supported by its run-2 pass (94 of 94), not proven by reading the diff. The R4 runs (g10a and g3) are all at `58340e0`, a clean tree. This is a statement about the code, not a re-measurement, and it is scoped that way wherever the numbers are used.
**R2 definition.** Per forget request, on the Postgres clock. The logical lag is `logical_lag_s`: the time from `requested_at` until every sink was verified absent by query. The physical lag is `physical_lag_s`: the time from the request until the maintenance window's verified-absent time for every location. Sources are the two g8 manifests of record, `result.lag_report.requests` (6 requests per run) and `result.lag_report.sinks` (per-sink median, min, max and n). **Denominator: requests.** Per run there are 5 ad-hoc requests submitted back to back (so not independent) and 1 generator-owned subject. Reported per run and pooled (2 runs, 12 requests) as median, min, max and n. The per-request, per-sink rows are not in these manifests, so per-sink values are the manifests' per-run summaries and are not pooled. Wording: always "logical" or "physical"; the physical lag is **measured in this schedule** (set by when the g8 check's maintenance window ran) and is not a minimum latency; topics are compacting (the g8 setting, which broker removal needs); `pg_wal`, `qdrant_wal` and `spark_spill` are bounded, not removed.
**R4 definition.** The sum, over fault executions, of the reconciler's `dupes`, `losses` and `resurrections` at the gate after recovery, read from `result.faults.<id>` of the two g10a runs of record (default and compacting topics, 7 fault rows each), plus the g3 kill phase. Groups: replay (F1, F2), crash or restart (F3, F4, F5), schema (F6a, F6b), and the g3 kill row. The g3 row is read from `result.kill.kills` (3 SIGKILLs: `before_merge`, `mid_merge`, `after_merge`) and from the ground-truth compare in the check named "kill: silver equals ground truth", whose `detail` holds `missing`, `differing`, `extra_live`, `resurrected`, `duplicates`, `tombstone_pii`; `missing` is reported as losses. **Denominator: runs and fault executions** ("0 in N runs", never a rate): 3 runs, 14 fault executions and 3 kills. Wording: "idempotent under the tested faults", never exactly-once; silver only, because bronze holds duplicate rows by design (the F1 replay ledgers); F4's retry ran with no concurrent writers; F5 is a graceful restart of a dev-container broker; one machine and no extrapolation.
**Pre-registered, so it cannot be chosen after the fact: the Connect-stall counting rule.** ADR-0020 records a silent Connect stall after the F5 broker restart (cause unverified, user decision open). If a future run of record shows it again, that run stays in the denominator, its F5 outcome is `gate_failed` (never `self_healed`), and its cut-time `losses` are reported as observed; a separate figure after an operator Connect restart may be added but does not replace it. The notebook prints the ADR-0020 open finding beside R4, verbatim, read from that ADR at run time. G11a changes no Connect or client setting.
**Sleep check (a recorded fact, not computed).** Both g8 run windows were checked by hand against `pmset -g log` and contain no host sleep (details in Measured). It is a fact in this ADR and not a notebook output because the power log rotates and would not reproduce later.
**R1 is deferred, and its design is pre-registered here only in outline.** The design is: a black-box sentinel prober (inserts into `help_articles` every 10 s, silver polled every 3 s and Qdrant every 6 s) beside instrumented capture points (t0 from the generator's run log, t_broker from the bronze `kafka_ts` under LogAppendTime, t_silver from the foreachBatch event log, t_qdrant from the embedder's `wait=true` ack); 4 pre-registered rate points with 5 independent rounds each, each round a fresh stack of about 50 minutes; and automatic sleep guards (a `pmset` parse plus a wall-versus-monotonic clock check) that invalidate a run instead of dropping it. Its exact definitions, points, validity guards, wording and the false-alarm denominator **will be written in their own ADR before any R1 run**, and that ADR may change this outline. Until then no R1 number exists, and no R1 claim, resume figure or README value is made.
**Tooling.** `duckdb` is pinned in `requirements-dev.txt` and `requirements-dev.constraints.txt` at the newest release uploaded on or before the policy cutoff of `scripts/pin_policy.py` (2026-10-11), the way xxhash was added. The notebook is a percent-format Python file, run as a script by `make g11a-results`, covered by mypy and by a test that runs `main()` on synthetic manifests. Every string it writes passes `adrp.recon.classify.wording_violations`, `adrp.measure.report.wording_violations_g11a` (which also bans percentile wording at these sample sizes) and a 13-digit-number scan (epoch milliseconds and raw ids). The README R2 and R4 cells are written by hand from the rendered strings and then checked mechanically against them.
## Limits
- R2 is 2 runs and 12 requests on one machine, 10 of them in two batches submitted within a few seconds of each other. It supports "in these runs", nothing about other schedules or other scales.
- The physical lag depends on the g8 schedule: the maintenance window runs when the check runs it. A different schedule would give different physical lags, so the number is no latency floor.
- R4's zeros are counts over 3 runs. They do not show that undetected faults are absent (ADR-0023), and the six faults are a subset.
- The F4 retry staleness case (a transaction held open across the retry) and a hard broker crash are untested (ADR-0020).
- R1 is not measured: no freshness figure exists.
