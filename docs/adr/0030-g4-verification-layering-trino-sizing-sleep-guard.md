# ADR-0030: G4 verification layering, the g4-check list, Trino sizing and the host-sleep guard
- Status: accepted (G4, 2026-11-10); written before any G4 run, so nothing here is a result. Items marked **unverified** are not yet observed. The fixture catalog is settled (Step 0 spike result below). The Measured section is added after the run of record.
## Decision
**Layering.** G4 is verified in four layers, cheapest first:
1. A pure-Python oracle (`adrp.gold.oracle`) with Hypothesis tests (1,000 cases): shuffle and duplicate invariance, contiguity, no zero-length LSN intervals, entries net to zero; and a deterministic test that the ledger from the generator's ops for 2,000 transactions reproduces the generator's final balances. No Docker.
2. **FX**, `scripts/g4_fixture.py`, run by `make dbt-fixture`: a throwaway Trino container (`adrp-ci-trino`, port 28080) that does not touch the shared stack, runs in CI and locally, and asserts against the oracle on scripted data.
3. **LIVE**, `scripts/g4_check.py`, run by `make g4-check`: destructive (clean volumes), on the real CDC path, Lakekeeper and SeaweedFS. This is the run of record.
4. Static checks: `tests/test_dbt_gold_static.py` and `dbt parse` (no Docker).
A full-stack run cannot be avoided for three done conditions: balances against the real Postgres `accounts.balance`, SCD2 against the generator's ground truth through real CDC, and dbt against the real Lakekeeper and SeaweedFS catalog. Everything else is proven in FX or pure Python.
**Fixture catalog: Iceberg `TESTING_FILE_METASTORE` on the container's local filesystem (decision D4, settled by the Step 0 spike, 2026-11-10).** No fallback was needed. The planned property names were partly wrong on Trino 483 and the spike found the working ones in the server log: `fs.native-local.enabled` is replaced by `fs.local.enabled`, and `local.location` must name a directory that already exists, so `/tmp/fx` failed at startup. The working `infra/trino/ci/catalog/fx.properties` is `connector.name=iceberg`, `iceberg.catalog.type=TESTING_FILE_METASTORE`, `hive.metastore.catalog.dir=local:///fx`, `fs.local.enabled=true`, `local.location=/tmp` (the metastore creates `/tmp/fx` itself; no mounted volume). **Step 0 spike result.** One throwaway container (`adrp-spike-trino`, 2 GB, the mounted `jvm.config` and `config.properties`, image `trinodb/trino:483`, Iceberg 1.11.0 inside) came up in about 10 s. Through the Python trino client, `CREATE SCHEMA`, `CREATE TABLE`, `CREATE TABLE AS SELECT`, `INSERT`, `DELETE` and `DROP SCHEMA ... CASCADE` all worked, on an unpartitioned and a `partitioning = ARRAY['d']` table. `$snapshots` summaries after a `DELETE`: on the unpartitioned table, and on the partitioned table for a predicate that is not a whole partition, the snapshot has `operation = delete` and `added-position-delete-files`, `added-delete-files` and `added-position-deletes` (9 and 7 in the spike), with `total-records` unchanged (30), so `deleted-records` is absent; on the partitioned table a `DELETE` of a whole partition is a metadata delete with `deleted-data-files`, `deleted-records` (10) and `removed-position-delete-files`, and no added keys. No equality deletes appeared. This is why the FX5 backfill check accepts `added-position-deletes` as delete evidence (already amended in the list below). `docker stats --no-stream` showed 934 MiB of the 2 GiB after the spike queries. The dbt-trino `delete+insert` incremental, the snapshot and the contract were not part of the spike; they were then exercised by the fixture (`make dbt-fixture`, 5 dbt_fixture nodes and 70 FX checks passed, 99 s), which also found two project fixes: the `is_incremental` override on the full-build unit test, and no enforced contract on the snapshot (ADR-0028 amendment).

**Step D live smoke (2026-11-10, not a run of record).** Trino 483 was started next to the running stack (the stack left by the g8 run of record) with the `lake` REST catalog and SeaweedFS S3; it was healthy at 795 MiB of 2 GiB. `make gold-build` built every model, test and the snapshot against the real lake in 25 s: PASS 43, WARN 1, ERROR 0. No REST, S3 or conditional-write problem appeared, so `s3.exclusive-create` was not needed. The one warning is `assert_ledger_balance_matches_silver_accounts` (warn severity without `strict_reconcile`) for 1 account. Cause: 6 live silver accounts have no `public.accounts` events left in bronze, because that g8 run's forget workflow physically removed the subjects' bronze rows; with no create event the ledger has no opening entry. 5 of the 6 opened at a 0 balance, so their ledger sum still matches, and 1 opened at 66.20, which is the mismatch. This is the pre-registered limit of ADR-0027 and ADR-0029 (gold is not covered by the forget workflow until G8b, and rebuilding from bronze after a forget is lossy), not a gold-model defect. g4-check starts from clean volumes with no forget, so the strict test applies there. Trino was stopped afterwards; the `lake.gold*` tables stayed until the next volume wipe.
**Trino sizing (decision D3).** `trino` stays in compose profile `transform`. `mem_limit` goes from 3g to 2g with `-Xmx1536m` in a mounted `jvm.config` (replacing the image's `MaxRAMPercentage`), and `query.max-memory` and `query.max-memory-per-node` are 512 MB in a mounted `config.properties`. The design table changes to "+2 GB". The Docker VM is 7.67 GiB; the core and apps `mem_limit`s sum to about 11.4 GB although real use was about 3.0 GB when inspected. g4-check therefore skips `embedder`, `dagster` and `exporter`, which G4 does not need (up to about 4.2 GB of limits). Never run `make ci` and a g-check at the same time. The `lake` catalog file is mounted as a single file so the image's default `memory` catalog stays for `dbt_fixture` (decision D12, kept as the adapter smoke test). The `trino` service has no `depends_on`, because it would cross profiles.
**"make ci runs locally" change.** `dbt-fixture` starts its own throwaway Trino on :28080 in the style of `contracts-ci`, and CI runs `make dbt-fixture` instead of using a Trino service container. This is recorded because it changes how `make ci` is run: it needs Docker Desktop, does not touch the compose stack, and uses about 2 GB more VM memory for a few minutes.
**Host-sleep guard (decision: automatic).** The only existing sleep check is the manual `pmset` check in ADR-0024. G4 adds `scripts/hostsleep.py` (`SleepGuard`), used by g4-check. A run is **invalid** if either check fires: a `Sleep`, `Wake` or `DarkWake` event in `pmset -g log` inside the run window, or a drift of more than 2 s between wall-clock time and `CLOCK_UPTIME_RAW`. Outside Darwin the result is `{"platform": ..., "checked": false}`. An invalid run is noted in this ADR as an attempt and rerun. `scripts/manifest.py` is unchanged; the guard's result goes into `result`. `caffeinate` does not stop lid-close sleep, so runs of record are done with the lid open and on power.
**Run discipline.** A clean tree is required for the run of record (`.gitignore` entries for `dbt_gold/target`, `dbt_gold/logs`, `dbt_gold/dbt_packages`, `dbt_gold/.user.yml` must exist first, or the manifest shows `git_dirty`). Checks use labels A, B and M for scripted rows and never print or store raw ids; ad-hoc ids have 13 digits and a manifest scan flags them. The pre-registered budget is under 30 minutes for g4-check (an estimate of 18 to 25, not a result).
**Regression rule (Step G).** After the run of record, `git diff --stat 9ef8a2c <record-sha>` over `src/adrp/spark`, `forget`, `embed`, `gen`, `recon`, `src/adrp_orch`, `docker`, `infra/connect`, `infra/postgres`, `infra/redpanda`, `infra/seaweedfs` and the unchanged g-check scripts (`bootstrap.py`, `g2`, `g3`, `g6`, `g8`, `g10a` checks, `reconcile.py`, `manifest.py`, `generate.py`) must be empty, and the core and apps compose render must be unchanged. If both hold, no g3, g6, g8 or g10a rerun is made, and the README shows the diff command. If not, the rerun follows the changed area (spark or g2/g3 helpers: g3-check; `embed`: g6-check; forget, bootstrap or broker config: g8-check; recon or fault code: g10a).
## The g4-check list (pre-registered)
Layers: **FX** is deterministic and runs in the throwaway Trino; **LIVE** is the run of record.
| Done condition | FX | LIVE |
|---|---|---|
| `dbt build` passes | Every build step succeeds; `run_results.json` statuses are all `success` or `pass`. | `check("dbt: build #k passed (models, tests, snapshot)")` for every build; counts parsed from `dbt_gold/target/run_results.json`. |
| Ledger nets to zero per transaction | Singular tests `assert_ledger_nets_to_zero_per_journal` and `..._per_transaction`. | Trino query: `group by journal_id having sum(amount) <> 0` returns 0 rows, and the same by `transaction_id` (payment plus its refund reversal) returns 0 rows. |
| Balances reconcile to Postgres `accounts.balance` | Ledger balance equals silver `accounts.balance` (`assert_ledger_balance_matches_silver_accounts`, severity `error` in FX). | At a quiescent cut (generator finished, scripted writes done, `g3_check.Drain.wait_silver()` true, then a build): for every account in Postgres (`SELECT id, balance FROM accounts`), the ledger sum (`account_id > 0`) equals the balance. Report n accounts, 0 mismatches, and accounts with no entries. |
| SCD2 matches ground truth for a scripted change sequence, including several changes between dbt runs | Scripted bronze events against `adrp.gold.oracle.scd2_versions`. Scenario: insert; 2 updates in separate transactions plus 1 transaction with 2 updates to the same key, all between run 1 and run 2; duplicate bronze rows; out-of-order arrival. | (a) Generator customers: 1,000 transactions, build 1, then 500 more, build 2. `dim_customer` versions per customer equal the generator ops (`g2.generator_ops`) in LSN order; `valid_from` equals the run log `commit_ts` truncated to ms, joined via `txn_no`; `txid` equals `xid32`. (b) Scripted customers A and B and merchant M via psql between builds 1 and 2; expected versions from the oracle over the scripted list, each scripted transaction capturing `txid_current()` and then `pg_xact_commit_timestamp`. Also: one current row per key, contiguous intervals, no zero-length interval by LSN. |
| One-day backfill reproduces identical results | Backfill of day D: checksums before equal after, and the backfill snapshots show delete evidence (`deleted-records`, `added-position-deletes` or `added-equality-deletes` > 0; Trino writes position-delete files on unpartitioned Iceberg tables, so `deleted-records` alone may be 0) and `added-records > 0`, so the check is not vacuous. Amended before any run. | Same for D = 2026-01-01 (all generator rows), with scripted rows dated 2026-01-02 and 2026-01-03 left untouched. Checksum: `adrp.recon.canonical.digest` (sum of `xxhash64` mod 2^64) over every row of `fct_transactions` and `fct_ledger_entries`, fetched through the `trino` client. Evidence from the Iceberg `"fct_ledger_entries$snapshots"` summary. |
| dbt snapshot loses intermediate changes | Snapshot after run 1 and run 2: customer A is captured in exactly 2 states while SCD2 has 4 versions, so exactly 2 are lost (asserted). | Scripted A: 2 lost (asserted). For all generator customers, report "k of n customer versions were not captured by the snapshot at 2 dbt runs in this run". Not asserted, because it depends on the schedule. |
| Supporting checks | Late arrival within the lookback is picked up; beyond the lookback it is missed, `assert_gold_complete_vs_silver` fails (expected), and a backfill recovers it. A contract break fails the build. An idempotent rerun. A re-key flows to `fct_transactions` and leaves the ledger unchanged. | Idempotent rerun (build 3 with no new data: every gold checksum unchanged and the ledger `entry_id` set unchanged). Incremental equals from-scratch (`--target rebuild` into `gold_rebuild`, checksums equal excluding the one re-keyed transaction, then drop it). The re-keyed transaction is checked separately: it differs only in the carry-forward fields (`first_lsn`, `customer_sk` in `fct_transactions`; `source_lsn`, `src_source_ts` on its ledger legs), because the incremental run keeps first-seen values and a rebuild derives them from the current silver row. A backfill of a day that contains a re-keyed transaction is therefore not checksum-identical; the backfill days used (2026-01-01 live, 2026-01-02 fixture) contain none. Amended before any run. Re-key flow (psql `UPDATE transactions SET customer_id = <placeholder>` for one of A's transactions, folded into build 2). Artifact hygiene (no canary in `dbt_gold/target` or `logs`). Host-sleep guard. |
**LIVE phases:** P0 guard start and wait for Trino and `lake.bronze.cdc_events` (Spark creates each silver table on its first rows, so silver visibility is waited for after the P1 drain; corrected after attempt 1, which aborted at P0 on fresh volumes before any gold check ran); P1 generator 1,000 transactions, scripted M and A (canary email `g4canary-...@example.invalid`) and money moves dated 2026-01-02 and 2026-01-03, drain, build 1 with `strict_reconcile`; P2 500 more transactions, scripted A, B and M sequence plus the re-key, build 2; P3 build 3 (idempotent); P4 backfill 2026-01-01; P5 `--target rebuild` equivalence, then drop `gold_rebuild`; P6 canary grep; P7 guard stop. Data size is 1,000 plus 500 generator transactions plus the scripted rows (decision D6). Dagster-scheduled dbt is out of scope (D8).
**Wording rules for everything G4 reports** (enforced by hand in G4; the `wording_violations` approach of ADR-0023 is the model if G11b adds a machine check):
- Idempotency: "rerunning `dbt build` on unchanged inputs left every gold checksum unchanged in this run", or "idempotent under the tested faults". No delivery-guarantee claim.
- Ledger: "append-only by construction; entries were unchanged across 3 builds and one backfill in this run". Not "immutable ledger" as a proof.
- Balances: "all n accounts matched Postgres `accounts.balance` at a quiescent cut, one run, one machine".
- Snapshot loss: "k of n customer versions were not captured at 2 dbt runs in this run", never a general percentage.
- SCD2: "matched ground truth for the scripted sequence and the generator's customers in this run". Never "lossless".
- Contracts: "only `not_null` is enforced by Trino and Iceberg".
- Forget: gold is not covered by deletion propagation until G8b. Every removal is stated as logical or physical.
- Late data: "picks up rows arriving within the 60-minute lookback; later rows are flagged by completeness tests (fixture-verified)".
- R6 and S4 are not reported as measured (G11b). Always "one machine, 1 run of record".
## Limits
- The FX layer proves behaviour on scripted data in a throwaway catalog that may differ from Lakekeeper and SeaweedFS (S3 conditional or exclusive-create writes, multipart, key vending are **unverified** until the live smoke and g4-check; if S3 writes fail, the Trino 483 `s3.exclusive-create` property is the first thing to check).
- The oracle is the author's model of the semantics. Agreement between the oracle and gold shows consistency with that model, plus ground truth from the generator's ops and Postgres where LIVE uses them.
- One machine and one run of record. A Trino out-of-memory kill would appear as dbt connection errors and is checked with `docker inspect` (`OOMKilled`).
- The sleep guard detects sleep that macOS logs or that shows as clock drift. It does not prove the absence of every pause.
